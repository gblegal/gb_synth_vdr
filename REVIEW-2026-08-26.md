## B1 — `consolidate_wave_incoming` silently corrupts the Gate-B registry

**Severity: high. Silent data corruption. `synthvdr/schema.py:456`.**

`skills/vdr-build/SKILL.md` §3 describes the intake as an upsert of "the author's finalised
`location` and `substance` wording". The implementation is:

```python
by_id[row["id"]].update(row)
```

— a full dict update of **every key the author sends**. A `vdr-author` subagent that returns
extra fields overwrites the signed-off registry with them. This is not hypothetical: my
`wave1-batch-a` author returned `workstream: COMM` (the ID prefix, not the workstream name), a
string-valued `corroboration`, and a rewritten `title`. I caught it only by reading the intake
before consolidating; nothing in the pipeline would have.

Reproduction (run from the repo with the package importable):

```python
import copy
from synthvdr.schema import consolidate_wave_incoming

master = {"schema_version": 1, "room": "X", "findings": [{
    "id": "IP-1", "title": "real title", "severity": "critical", "workstream": "ip",
    "multi_document": True, "source": "a.md", "corroboration": ["b.md"], "substance": "s"}]}
incoming = {"w1": {"findings": [{
    "id": "IP-1", "workstream": "IP", "corroboration": "b.md",
    "title": "author retitled", "location": "L", "substance": "S"}]}}

res = consolidate_wave_incoming(copy.deepcopy(master), incoming, {}, {"ip": "IP"})
print(res.findings_doc["findings"][0])
```

Observed:

| Field | Master | After upsert | Caught by `validate()`? |
|---|---|---|---|
| `workstream` | `ip` | `IP` | **No — passes clean** |
| `title` | `real title` | `author retitled` | **No** |
| `corroboration` | `["b.md"]` | `"b.md"` → loads as `['b','.','m','d']` | Yes, downstream |

The `corroboration` case is loud: `evidence_paths()` returns `['a.md','b','.','m','d']` and
`build_flagged_tree` raises `TwinError`. The `workstream` and `title` cases are the dangerous
ones — `validate()` returns no errors, so a corrupted registry ships. A wrong `workstream`
also feeds `derive_prefix_for_workstream`'s correspondence cross-check, which is the one thing
meant to catch a reordered `FINDING_PREFIXES`.

**Fix:** restrict the upsert to author-owned fields, and refuse a row that tries to change a
Gate-B-owned one.

```python
AUTHOR_OWNED = ("location", "substance")

for row in incoming.get("findings") or []:
    if row["id"] not in by_id:
        raise SchemaError(...)                      # existing check, keep
    target = by_id[row["id"]]
    conflicting = [
        k for k, v in row.items()
        if k not in AUTHOR_OWNED and k != "id" and k in target and target[k] != v
    ]
    if conflicting:
        raise SchemaError(
            f"{label}: finding {row['id']!r} tries to change Gate-B fields "
            f"{sorted(conflicting)} — consolidation refines only {AUTHOR_OWNED}"
        )
    target.update({k: row[k] for k in AUTHOR_OWNED if k in row})
```

Raising (rather than quietly dropping) is right: an author sending a conflicting `workstream`
has misunderstood its brief, and you want to see that.

**Tests to add** in `tests/test_schema.py`:
- a conflicting `workstream` raises rather than mutating the registry;
- a string-valued `corroboration` raises rather than becoming a character list;
- a row carrying only `location`/`substance` still upserts exactly as today (regression);
- a row echoing Gate-B fields *identically* is accepted (authors will echo their brief back).

**Also update** `agents/vdr-author.md` to state that the `findings:` intake carries `id`,
`location` and `substance` only. The current shape example shows a full finding row, which is
what invites authors to send the rest.

## B2 — `anchors.csv` tier does not mean what `/vdr-build` says it means

**Severity: high. Docs/implementation mismatch. `synthvdr/slots.py:95`, `skills/vdr-build/SKILL.md:22`.**

`skills/vdr-build/SKILL.md:22` defines the ordering rule as:

> sort the slot list by tier before batching, `A` (anchor — carries a finding, a distractor, or
> is otherwise load-bearing) before `F` (filler)

But `slots.py:95` assigns tier positionally, at `/vdr-scope` time, before any finding exists:

```python
tier = TIER_ANCHOR if position < max(1, round(count * 0.35)) else TIER_FILLER
```

The first ~35% of each section's slots are `A`; the rest are `F`. Tier has **no relationship
whatsoever** to the registry. In this room, **6 of the 10 registry evidence paths were tier
`F`** — including `5.2.1` (REG-1's corroboration), `6.2.1` (IP-1's corroboration), `16.2.1`
(OPS-1's source) and both DX-1/DX-2 trap documents. Following the rule literally would defer
half the findings' evidence behind every filler-tier anchor, and defeat the stated invariant
that "an interrupted build never strands a finding half-planted".

Two candidate fixes; I'd take the first.

1. **Re-tier after `/vdr-findings`.** Add a step to `/vdr-findings` (or a `synthvdr.slots`
   helper) that rewrites `anchors.csv`, promoting every path in `findings.yaml`'s
   `all_evidence_paths()` and `distractors.yaml`'s `location`/`resolution` to tier `A`. Tier
   then means what the skill says, and the depth floors follow — which is a bonus, since a
   finding's evidence arguably *should* clear an archetype floor rather than the 350-word
   tier-F floor. Note this changes existing rooms' floors, so gate it behind a schema/version
   bump or make it explicit in the skill.
2. **Reword `/vdr-build`.** Change the rule to "every registry evidence path first, then tier
   order", and correct the tier-`A` gloss to what it is: a structural depth/prominence tier
   assigned at scope time. Cheaper, but leaves the misleading word "anchor" in place.

Either way, `skills/vdr-build/SKILL.md:22` must stop claiming tier `A` carries findings.

## B3 — Cast masking still can't see a name broken across a line

**Severity: medium. High friction. `synthvdr/names.py:161`.**

HEAD fixed the case half of this (see R1) but the separator is still tab-and-space only:

```python
re.sub(r"[ \t]+".join(re.escape(word) for word in words), " ", text, flags=re.IGNORECASE)
```

Markdown prose wraps. `Solresse\nBeauty SAS` does not mask, so `entity_tokens` scans the
residue and reports `Beauty SAS` as an unchecked name. Over the run this produced **nine**
false positives across three separate rounds — `Beauty Inc`, `Beauty SAS`, `Beauty Holdings
Limited`, `Contract Filling Limited`, `Holdings Limited`, `SOLRESSE BEAUTY SAS` — and I wrote
the same reflow script three times. It also hit my own fact sheet during `/vdr-scope`, before
any document existed.

**Fix:** widen the separator to tolerate a single newline.

```python
r"[ \t]*\n?[ \t]*".join(...)   # or r"\s+" if you accept crossing blank lines
```

Prefer the explicit `[ \t]*\n?[ \t]*` over `\s+`: it matches a wrapped name without letting a
mask jump a paragraph break or a table-row boundary, which `\s+` would.

The docstring already reasons about whitespace flexibility ("a name wrapped across a table
cell or padded in a document is the same name") — it just stops short of the newline case that
actually occurs.

**Tests to add** in `tests/test_qa_leakage.py` (beside the existing all-caps controls):
- a cast name split across a line break masks, and gate 14 stays clean;
- a genuinely unknown name split across a line break is **still reported** (guard against the
  widened mask opening a blind spot);
- a mask does not jump a blank line.

**Related:** `skills/vdr-scope/SKILL.md` §3 tells the author to run `extract_candidates` but
never to run the mask-then-scan residue check. Add it — it is what actually predicts gate 14,
and running it at Gate A catches wrapped and undeclared names before a single document exists:

```python
from synthvdr.names import mask_cast_names, entity_tokens
residue = entity_tokens(mask_cast_names(fact_sheet_text, {v.text for v in verdicts}))
assert not residue, residue
```

## S1 — `/vdr-scope` invents the deal before it knows what the room will demand

**Severity: high design issue. `skills/vdr-scope/SKILL.md` §2 vs §4.**

§2 writes the fact sheet. §4 generates the slot manifest. So the deal is invented with no
knowledge of which sections exist or what their depth floors are.

The domain pack allocates a document to all 20 workstreams **even at XS(40)**, including
`13.1.1_trust-deed-01.md` and `4.1.1_facilities-01.md`, both of which classify as `longform`
with a **2,500-word floor**. A ten-year-old D2C skincare brand plausibly has neither a
defined-benefit pension scheme nor bank debt — and my Gate-A fact sheet said, in terms, "there
is no bank debt" and was silent on pensions and JVs.

The result: I had to retro-fit a £4.0m RCF, a DC master-trust pension arrangement and a 12.5%
minority stake into a fact sheet **the user had already signed off at Gate A**, purely so three
sections had something to be about. That is exactly the kind of post-Gate-A change the gate
exists to prevent.

**Fix:** swap the steps. Generate the slot manifest first (current §4), then write the fact
sheet against it (current §2). The interview in §1 already collects everything §4 needs — the
size preset is the only input. Then show the author the section/floor profile before they
invent anything:

```python
for slot in slots:
    print(slot.slot_id, slot.tier, floor_for(slot.slot_id, Path(slot.rel_path).name, slot.tier, pack))
```

and add a line to §2 along the lines of: *the fiction must support every section the manifest
allocates — check the longform slots (facilities, trust deed, information memorandum) and give
the group something real for each, or the room cannot be authored to its floors.*

**Alternative worth considering:** let XS/S drop workstreams the invented deal genuinely does
not have, rather than forcing 20 sections into 40 documents. A 40-document room spread over 20
workstreams is one document per subsection, which is also why the deliberate-gap allowlist had
to carry three entries for perfectly ordinary sibling references.

## S2 — `vdr-author` cannot count words, and its estimates are systematically high

**Severity: high friction. `agents/vdr-author.md` frontmatter.**

```
tools: Read, Write, Edit, Grep, Glob
```

No Bash. But the agent is told "Meet your slot's depth floor: tier A by archetype, tier F at
least 350 words" and asked to report word counts in its manifest. With no way to measure, every
author estimated — and every estimate was high:

| Slot | Author's reported count | `wordcount()` | Floor |
|---|---|---|---|
| 16.1.1 | ~1,450 | 1,190 | 1,200 |
| 6.1.1 | ~1,350 | 1,103 | 1,200 |
| 10.1.1 | ~1,300 | 1,050 | 1,200 |
| 17.1.1 | ~3,050 | 2,447 | 2,500 |

One author said so explicitly: *"the available grep tooling only counts matching lines, not
tokens, so these are conservative visual estimates"*. Another: *"this environment's tool set
has no shell access to run `wc -w`"*. Seven of 40 documents landed under floor, costing a full
remediation wave with two extra subagents.

**Fix (pick one):**
1. Add `Bash` to the agent's tools and tell it to verify with
   `python3 -c "from synthvdr.qa.depth import wordcount; ..."` — note `wc -w` is *not*
   equivalent (`wordcount()` counts CJK at half weight).
2. Better, and keeps the agent's tool surface tight: have `/vdr-build` run the depth lint
   per-batch **immediately after the wave returns and before consolidation**, and re-dispatch
   deficits. I ended up doing this by hand; it belongs in the skill as a numbered step between
   current §2 and §3.

Either way, delete the request for word counts from the agent's Return section, or mark them
explicitly as estimates not to be trusted. Right now the manifest reads as measurement.

## S3 — Gate 15 (and effectively gate 13) can't pass mid-build, but aren't excepted

**Severity: medium. `skills/vdr-build/SKILL.md` §6, lines ~331–344.**

§6 names gates 2, 7 and 8 as expected mid-build failures, then states:

> **Every gate other than these two is a real check on every wave, including the first**, and a
> FAIL on any of them is always a real defect

But the same skill runs `vdr-auditor` only "After the last wave", and gate 15 fails until every
finding is audited (SKILL.md:381 says so). **Every wave before the last necessarily fails gate
15.** Combined with §7's "do not start the next wave while any gate is failing outside Step 6's
named exceptions", the skill contradicts itself. I recorded wave 1 as PASS with gate 15 noted
as excepted, which is the only workable reading.

Gate 13 has a softer version of the same trap. Canonical figures must be present in the room;
if a figure's only natural home is a slot not yet authored, gate 13 fails through no defect.
`£48.0m` (enterprise value) and `£9.0m` (earn-out) belong in the draft SPA — `18.2.1`, a
tier-F slot that the ordering rule puts in the *last* wave. I had to pull it forward into wave
1 to make gate 13 answerable.

**Fix:**
- Add gate 15 to §6's named exception list, worded like gate 2: expected to fail on every wave
  until the auditor runs, and clearing is what tells you the audit is done.
- Add a sentence to §1's ordering rule: *any slot that is the canonical home of a fact-sheet
  figure counts as load-bearing and belongs in the anchor waves* — or except gate 13 mid-build
  the same way. The first is better; it keeps gate 13 a real check throughout.

## S4 — `/vdr-build` doesn't hand authors the room's own invariants

**Severity: medium. `skills/vdr-build/SKILL.md` §2.**

§2 lists what to give each author: slot list, index-src sections, fact-sheet extracts, and its
own registry rows. It does not mention four room-level facts that every author needs and that

| Invariant | Where it lives | What happens without it |

## S5 — `/vdr-findings`' severity ratio is unachievable below ~11 findings

**Severity: low. `skills/vdr-findings/SKILL.md:31`.**

> Aim for roughly a 1 : 3 : 4 : 3 split across critical / high / medium / low severity

That needs at least 11 findings. XS budgets 4 and S budgets 12. At XS the ratio scales to
0.36 / 1.1 / 1.45 / 1.1, which is not a split anyone can write. I used one per band, which

severity band and add to medium first* — or express the target as a per-preset table beside the

## S6 — No naming guidance, and the collision rate is ~40%

**Severity: low, but expensive. `skills/vdr-scope/SKILL.md` §3.**

Across scoping I ran roughly 30 WebSearches and **rejected 9 names**: `Hydraveil`, `Verith`,
`Solvane`, `Coravel`, `Marnelle`, `Aldermere`, `Lindmere`, `Tarnbeck`, `Quarrenden`. Each
rejection is a full round trip — invent, search, discard, re-invent — and `/vdr-scope` offers
no guidance on generating candidates likely to survive.

The pattern from this run is clear enough to encode:

- **Cleared first time:** `Brindlewick`, `Fenwold`, `Cardingham`, `Solresse`, `Cadenwall`,
  `Pellowe Harkness`, `Ravenhurst`, `Maisonvert` — multi-syllable compounds of uncommon
  English/place-name morphemes.
- **Collided:** `Verith`, `Solvane`, `Coravel`, `Marnelle` — short, vowel-heavy coinages, which
  are exactly what consumer-brand namers already mined out. `Coravel` was launched as a
  BlackRock/ACS data-centre JV six weeks before this run.
- **One letter off a real name is a rejection, not a pass.** `Verith` vs the real Verity Beauty,
  `Quarrenden` vs several real `Quarrendon` companies. Worth saying explicitly — it is a
  judgement call the skill currently leaves open.

Two further points for §3:

- **Check the distinctive token once, not each entity variant.** `Solresse Beauty Holdings
  Limited`, `... Limited`, `... SAS` and `... Inc` share one distinctive token; one search on
  `Solresse` covers all four. The skill's "one WebSearch per distinctive name" reads as
  per-row and inflates the cost fourfold on a normal entity tree.
- **State the tool's geographic bias in the caveat.** The skill's honest-limit paragraph
  mentions dormant companies and non-English markets. It should also say the available
  WebSearch is US-weighted, which is a real weakness when the invented group is British and
  French — precisely the shipped domain pack's centre of gravity.

## S7 — Consumed wave intake is never archived

**Severity: cosmetic. `skills/vdr-build/SKILL.md` §3.**

Consolidation globs `_key/incoming/*.yaml` every wave, so wave *n* re-reads every prior wave's
intake. It is safe — `findings:` upserts are idempotent and `new_findings:` is guarded by the
ledger — but the safety rests entirely on `parse_new_findings_ledger`, and the read cost is
O(waves²). On an XL room that is 20-odd waves re-reading the whole intake history each time.

**Fix:** either move consumed files to `_key/incoming/consumed/` after a wave's gates pass, or
add a sentence to §3 stating that re-reading is deliberate and that the ledger is what makes it
safe. The second is fine; right now the property is load-bearing and undocumented at the call
site.
